# CostBridge

付款时很果断，回头记账时却常常盯着账单发呆？CostBridge 想帮你省下这段思考人生的时间。

它接过 iOS 快捷指令的截图或文字，结合 iCost 里的分类和账户，整理出一笔待确认的账。你看过、点头之后，才会跳转 iCost；它不会自己替你写账本，也不保存原始账单。毕竟 AI 擅长一本正经地猜，钱还是交给你自己管。

[安装快捷指令 v0.5.0](https://www.icloud.com/shortcuts/7b87265906fc42b2b2eaf392651630d9) · [打开 CostBridge](https://cost.0211120.xyz/)

安装前准备好 iCost 和个人授权码。导入时填写授权码、iCost 默认账户，想让它记住特殊规则也可以写一段自定义提示词；没有就留空。

## 账单会去哪里？

快捷指令把截图、iCost 分类和账户以及当前时间，通过 HTTPS 交给 CostBridge；服务再把截图、名单和提示词发送给配置的 Groq 接口。识别结果仅用于本次响应。

本项目不主动保存原始账单，但部署商和模型服务商如何处理或保留数据，以各自条款为准；他们的平台日志不由本项目控制。截图可能带着不少个人信息，发送前请看一眼。真实截图、账单、密钥和账户配置也别提交到公共仓库——Git 的记性比我们好。

模型会犯错，商品信息不清楚时尤其容易发挥想象力。每次入账前请核对结果。可选的自定义提示词由模型结合账单判断，结果需要人工核对。旧版快捷指令的 Apple Pay/0822 规则仍可使用。账户未知时使用指定默认账户并提示。模型未给出有效金额、日期或分类时停止，不生成成功结果。

## 给维护者：更新与发布

服务版本以 `package.json` 和 [更新记录](CHANGELOG.md) 为准；快捷指令单独标记版本。每次修改从 `codex/` 分支发起 PR，说明改动和验证结果，并等待自动测试通过。合并前检查版本号和更新记录：修复递增补丁号，新功能递增次版本号，不兼容变更递增主版本号。合并 `main` 后由 Vercel 自动部署，确认线上功能正常后创建对应的 GitHub 版本标签和 Release。快捷指令变更另行更新其版本标识并确认同步。

## 自己搭一座桥

需要 Node.js 20 或更高版本。参考 `.env.example` 设置环境变量：`UNKEY_ROOT_KEY` 是仅有目标授权空间验证权限的 Unkey 管理密钥，`GROQ_API_KEY` 是配置在服务端的 Groq API 密钥；当前使用 `qwen/qwen3.8-27b` 模型。设置后运行 `npm start`，服务监听 3000 端口。不要将密钥放入命令历史或公开文件；使用本机安全的环境变量管理方式。执行 `npm test` 运行离线测试。`.env.example` 只是变量说明，Node 不会自动读取 `.env`。

## 给喜欢直接对话的程序：接口

`POST /api/analyze`，头部 `Authorization: Bearer <服务访问凭据>`、`Content-Type: application/json`。模型密钥由服务端提供，无需在请求中传入。一次传 `image`（JPEG 文件的纯 Base64，不含前缀和换行）或 `text`，二选一。示例均为虚构数据：

```json
{"text":"午餐 12.50 元","expenseCategories":["餐饮","其他"],"incomeCategories":["工资"],"accounts":["信用卡","储蓄卡"],"defaultAccount":"信用卡","customPrompt":"Apple Pay 使用信用卡","now":"2026/11/07 16:06"}
```

成功示例：

```json
{"ok":true,"transaction":{"type":"支出","amount":-12.5,"currency":"CNY","date":"2026/11/07 16:06","category":"餐饮","account":"信用卡","remark":"午餐","warnings":["账户未识别，使用默认账户，请核对。","分类由模型判断，请核对后再入账。"]},"icostUrl":"iCost://expense?amount=12.5&currency=CNY&..."}
```

请求可选设置 `customPrompt` 为自定义规则文本（最多 2000 字，留空表示不使用额外规则），例如“Apple Pay 使用信用卡”。规则由模型判断，账户仍须来自账户列表。旧版 `ruleAccount` 在未提供 `customPrompt` 时继续启用原 Apple Pay/0822 规则。

小票显示 Groq 本次响应返回的今日剩余请求次数及请求耗时；若 Groq 未提供限额，小票显示“未提供”。旧请求中的 `showTokens` 不再影响小票，token 用量仍记录在后台诊断日志中。

失败返回非 2xx 状态和 `{"ok":false,"error":{"code":"...","message":"..."}}`；无论请求或模型失败，都不代表已入账。Vercel 请求体上限 4.5 MB；Base64 会增加约三分之一体积，建议截图转 JPEG 并缩小后控制在约 3 MB 以下。如平台在到达函数前拒绝超大请求，可能返回平台自己的错误而不是上述 JSON。

## 部署到 Vercel

导入本仓库创建独立项目，Framework 选择 Other，Node 运行时使用项目声明的版本。在项目环境变量中设置 `UNKEY_ROOT_KEY` 和 `GROQ_API_KEY`，部署后以 HTTPS 调用 `/api/analyze`。测试和生产环境分别使用独立授权空间和凭据；不要分享包含服务访问凭据的快捷指令。Vercel 和 Groq 平台可能产生费用，以各自当前套餐为准。

## 想自己动手做快捷指令？

现成的安装链接在上面。如果你想自己搭，也欢迎；先留着原有可用版本，新建一条来测试：

1. 在付款详情页触发指令，用“截屏”获取当前屏幕，转为 JPEG，按需缩小图片后使用 Base64 编码，并设置为不换行。
2. 按现有指令查找支出二级分类、收入分类和账户，整理为文本列表。设置存在于账户列表中的默认账户，并可选填写自定义提示词；当前时间格式化为 `yyyy/MM/dd HH:mm`。
3. 建立 JSON 字典，使用接口字段 `image`、`expenseCategories`、`incomeCategories`、`accounts`、`defaultAccount`、`customPrompt`、`now`，用“获取 URL 内容”向服务发 POST 请求。请求头添加 `Content-Type: application/json` 和 `Authorization: Bearer <你的服务访问凭据>`。此凭据只用于访问 CostBridge，不是模型密钥。
4. 如网络动作报错或 `ok` 不为真，显示错误并停止。成功时从 `transaction` 展示收支、金额、时间、账户、分类、备注和所有 `warnings`，提供确认和取消选项。
5. 选择确认后，打开响应中的 `icostUrl`；该链接根据 iCost 官方文档生成。先用虚构数据检查生成的链接，不要打开入账链接；确认无误后由你决定是否启用。打开链接或返回快捷指令均不能单独证明记账成功。

测试时用虚构交易文本就够了，不必让真实账单先上场。确认流程可靠，再拿自己的账单试用。

## 关于日志和额度

出问题时总得留点线索，但不必把账单也留下。调用诊断日志在 Vercel 响应后写入数据库：记录请求时间、请求编号、状态与错误代码、阶段耗时、输入类型与长度、模型和 token 用量；不保存凭据、账单正文、截图或识别结果。每天清理超过 7 天的记录。数据库故障或函数超时时记录可能缺失；Vercel 在函数启动前拒绝的请求也不会写入此表。`CALLLOG_DATABASE_URL` 用于连接日志数据库，`CRON_SECRET` 用于保护清理接口。

Groq 响应包含限额信息时，调用诊断日志同时保存限额、恢复时间和采集时间。网页自动读取最近一次快照，无需访问凭据，也不调用模型。额度快照可公开查看。快照并非实时额度，恢复时间从采集时刻起算；到达恢复时间后网页按满额估算并标记，实际额度可能因其他调用不同；日志写入失败或超过保留期时可能没有记录。本地服务不写入调用日志。`GET /api/quota` 公开返回最新限额快照。

### 创建访问 Key

`POST /api/create-key` 供快捷指令创建访问 Key。请求头使用 `Authorization: Bearer <Unkey Root Key>`，请求体为 `{"name":"名称"}`。服务端用 `UNKEY_CREATE_API_ID` 固定目标 API，直接将 Root Key 转交 Unkey，不将 Root Key 或生成的 Key 写入应用日志或数据库。该凭据由调用方保存在快捷指令中；密钥持有不等同于本人身份认证，使用该接口须信任部署服务及其托管商。服务商可能记录的请求信息取决于其配置。

接口的业务结果统一返回 JSON：成功为 `{"ok":true,"message":"...","key":"..."}`；失败时 `ok` 为 `false` 且 `key` 为空。客户端必须在复制前检查 `key` 非空。网络中断时 Unkey 可能已创建 Key，不应自动重试，应先检查后台。
